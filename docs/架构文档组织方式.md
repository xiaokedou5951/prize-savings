# 架构文档组织方式

> 项目：Prize Savings（去中心化储蓄抽奖应用）
> 适用形态：pnpm monorepo + 单团队，5 个模块（contracts / frontend / subgraph / keeper / packages），安全敏感的 Web3 DeFi 协议
> 本文件只回答一个问题：**架构文档放在哪、写什么、何时更新**，是"文档的文档"，本身不承载具体架构内容。

---

## 1. 组织原则

| 原则 | 含义 |
|------|------|
| **就近原则** | 模块内部细节写在模块自己的 `ARCHITECTURE.md`；只有跨模块、系统级的内容才进 `docs/`。避免中心文档膨胀。 |
| **单一事实源（SSOT）** | ABI、合约地址、TS 类型、subgraph schema 由代码/生成器产出，文档只**指向**它们，不复制粘贴，防止漂移。 |
| **写"为什么"，不写"是什么"** | "是什么"读代码即可；文档只保留无法从代码反推的**决策依据、权衡、不变量、模块契约**。 |
| **图优先于文字** | 模块关系、资金流、状态机一律用 Mermaid（代码即图，可评审、可 diff），文字仅作图注。 |
| **精炼、可淘汰** | 每个文档必须回答一个明确问题；回答不了或已由代码自明，则删除或合并。文档越少越健康。 |

---

## 2. 三层结构

```
docs/                                 # Tier 1 · 系统级（跨模块，唯一中心文档区）
├── README.md                         #   文档索引：各文档地图 + 导航
├── prd/
│   └── prize-savings-lottery-design.md  #   冻结的产品/协议设计（v0.1，只读，回答"要做什么"）
├── architecture/
│   ├── overview.md                   #   系统概览：定位、模块地图、核心数据流、架构权衡
│   ├── contracts.md                  #   合约架构：合约清单、接口、状态机、不变量
│   ├── module-contracts.md           #   跨模块接口契约（粘合层）
│   └── deployment.md                 #   部署拓扑：链、地址、环境变量、keeper 形态
└── decisions/                        #   架构决策记录 ADR
    ├── ADR-0001-*.md
    └── ...

contracts/ARCHITECTURE.md             # Tier 2 · 模块级（就近存放）
frontend/ARCHITECTURE.md
subgraph/ARCHITECTURE.md
keeper/ARCHITECTURE.md
packages/contracts/README.md          # 纯 SDK 型包用 README 即可，不必 ARCHITECTURE.md

（Tier 3 · 代码即文档）
contracts/src/…                       # 合约接口 + NatSpec 注释 = 权威
packages/contracts/src/…              # ABI/地址/viem 封装生成的类型 = 权威
subgraph/schema.graphql               # 索引 schema = 权威
```

**边界划分**（写入哪一层，一句话判据）：

- 涉及 **2 个及以上模块** 的约定（谁依赖谁、ABI 由谁生成、事件如何被索引）→ `docs/architecture/`。
- 只影响 **单个模块内部** 的组织/选型/目录 → 该模块的 `ARCHITECTURE.md`。
- 能在 **16 行内用代码或注释** 说清的 → 不写文档。

## 3. 文档清单（本项目最小集）

| 文档 | 位置 | 回答的问题 | 责任方 | 更新触发 |
|------|------|-----------|--------|----------|
| `README.md` | docs/ | 有哪些架构文档、从哪读起 | 架构负责人 | 新增/删除文档时 |
| `overview.md` | docs/architecture/ | 系统是什么、由哪些模块组成、资金如何流转、关键权衡 | 架构负责人 | 模块边界或数据流变化时 |
| `contracts.md` | docs/architecture/ | 核心合约各自职责、继承/依赖、状态机与不变量 | 合约负责人 | 合约增删、接口/不变量变化时 |
| `module-contracts.md` | docs/architecture/ | ABI/事件/subgraph schema/TS 类型如何单源生成与共享 | 集成负责人 | 接口或生成链路变化时 |
| `deployment.md` | docs/architecture/ | 部署在哪些链、地址、keeper 跑的什么、环境变量约定 | 运维/部署 | 每次部署或链变化时 |
| `ADR-00XX-*.md` | docs/decisions/ | 某个"不可逆/代价高"的决策为何这么做 | 决策人 | 仅新决策时追加，旧的不改 |
| `ARCHITECTURE.md` ×5 | 各模块根目录 | 本模块内部组成、依赖、选型、与系统的衔接点 | 模块负责人 | 模块内部结构调整时 |

> 已有设计文档 `docs/prd/prize-savings-lottery-design.md` 定位为**冻结的产品/协议设计**（v0.1），回答"要做什么"；`docs/architecture/` 系列定位为**活文档**，回答"长成什么样、为什么、如何衔接"。二者分工不重复：PRD 只读冻结，活文档仅在 `overview.md` 中引用它。

## 4. 各文档内容要点

### 4.1 `overview.md`（≤ 1 页）
- 一句话定位 + 指向 `../prd/prize-savings-lottery-design.md` 的链接。
- **模块地图**：一张 C4 Container 图，标 5 模块 + 外部依赖（ERC-4626 收益源 / Chainlink VRF / Automation）。
- **核心数据流**：deposit → yield → liquidation → prize pool → draw → claim 一条链，标清各环节由哪个模块负责。
- **架构权衡清单**：本期 5 个以内（如 MVP 用 VRF 半自动开奖而非 PFDA、单资产单奖币、contracts 不入 workspace）。

### 4.2 `contracts.md`（本项目重中之重）
- **合约清单表**：合约名 / 职责 / 参考实现 / 状态。
- **依赖与继承图**：一门 Mermaid classDiagram 表达接口与继承。
- **状态机 + 不变量**：明确"零损失"（`totalAssets() >= totalSupply()`）、"份额守恒"、"TWAB 只读追溯"三条不变量，标注在哪段测试中被验证。
- **资金流与权限**：哪些角色（owner/keeper/claimer）能对资金做什么。

### 4.3 `module-contracts.md`（粘合层，最易漂移，必须显式）
- **ABI/地址/类型生成链路**：`contracts` → 生成 → `packages/contracts` → 被 frontend/subgraph/keeper 消费，画清谁是上游、如何 regenerate。
- **事件 → subgraph 映射**：合约抛出的事件如何在 `schema.graphql` 中落成实体。
- **keeper 与合约的交互面**：keeper 调用哪些函数、订阅哪些事件、凭什么获得激励。

### 4.4 `deployment.md`
- 链配置（网络名 / chainId / RPC）、已部署地址表、`.env` 变量清单（与各模块 `.env.example` 对应）、keeper 运行形态（常驻进程 / 定时任务）。

### 4.5 模块 `ARCHITECTURE.md`（每个 ≤ 1 页）
- 本模块职责一句话、内部目录结构、依赖的外部模块/服务、与系统的衔接点（指向 `module-contracts.md` 相关小节）、本模块内的关键取舍。

## 5. ADR 约定

- 命名：`ADR-{4位序号}-{kebab-case 标题}.md`，序号只增不改。
- 触发门槛：**只有"不可逆或代价高"的决策才写 ADR**（工具链选型、模块拆分、协议机制取舍）。可随时改的小事不要写成 ADR。
- 模板五要素：`状态(提议/已接受/已废弃)`、`背景`、`决策`、`后果(正/负)`、`备选方案(被否的)`。
- 本期应补记的存量决策（已发生、未记录）：

| ADR | 主题 |
|-----|------|
| ADR-0001 | pnpm monorepo，且 contracts 不入 workspace（Foundry 无 node 构建需求） |
| ADR-0002 | 合约工具链采用 Foundry + Solidity 0.8.24（OZ v5 / Chainlink 兼容） |
| ADR-0003 | MVP 用 Chainlink VRF + Automation 半自动开奖，替代 PFDA 去中心化开奖 |
| ADR-0004 | M0 单资产 USDC + 单一奖币起步（窄而深） |

## 6. 图表规范

- 全部用 **Mermaid**，以代码块内联在 md 中，不存二进制图（不做 png/drawio 源文件）。
- 图型选型约定：模块/依赖关系用 `flowchart`；模块职责边界用 `C4 Container`；交互时序用 `sequenceDiagram`；合约继承/接口用 `classDiagram`；资金/协议状态用 `stateDiagram`。
- 一张图只表达一层抽象，不做"万能大图"；图必须配一段图注说明"该图强调什么"。

## 7. 维护规则

**何时写 / 改：**
- 新增或删除一个模块、改变模块边界 → 更新 `overview.md` + 相关模块 `ARCHITECTURE.md`。
- 改动任何跨模块接口（ABI、事件、schema）→ **同 PR 内**更新 `module-contracts.md`，否则视为不完整提交。
- 合约接口或不变量变化 → 更新 `contracts.md`。
- 部署 → 更新 `deployment.md`。
- 做不可逆决策 → 追加一条 ADR（不修改旧 ADR，用"已废弃"状态标记）。

**何时不写 / 删：**
- 内容可被代码、NatSpec、`package.json` scripts 自明 → 不写。
- 文档超过 1 页仍答不清"回答了什么问题" → 拆分或重写，不堆砌。
- 长期（>3 个月）无人引用、已与现实不符 → 删除并在 ADR 或提交信息中留痕。

**一致性检查（可选，纳入 CI 提醒）：** 提交跨模块接口改动时，自查 `module-contracts.md` 是否同步；文档中引用的生成物路径与脚本 output 是否一致。
